# S01 · 行情层升级：完整盘口

> 日期：2026-09-20 ｜ 代码：`apps/server/src/market/local-book.ts`、`market-feed.ts`、`parse.ts`、`streams.ts`
> 引擎**没有改**：`book` 输入本来就不限档数。

---

## 一、为什么要改

原来订的是币安的**部分深度流** `<symbol>@depth20@100ms`：每 100ms 一份前 20 档完整快照，不用管序列号，
断线重连 100ms 内自动对齐。简单，但只有 20 档，带来三个问题：

| 症状 | 原因 |
| --- | --- |
| 盘口精度聚合到 100 / 1,000 只剩一两行 | 20 档在 BTCUSDT 上只覆盖约 2 USDT |
| 「前方排队」经常只能给估算值（带 `≈`） | 挂单价超出可见 20 档就看不到真实挂单量 |
| 市价单动不动被「吃穿深度」拒掉 | 可见深度太浅，校验链第 11 步（最多吃一半可见深度）很容易触发 |

---

## 二、币安的规则

《How to manage a local order book correctly》（2026-09-20 核对），六条：

1. 先开着增量流 `<symbol>@depth@100ms`，把推送**缓冲**起来
2. 拉一份 REST 快照 `GET /fapi/v1/depth`，记下 `lastUpdateId`
3. 丢掉 `u < lastUpdateId` 的增量
4. 第一条要处理的增量必须满足 `U <= lastUpdateId <= u`
5. 之后每条的 `pu` 必须等于上一条的 `u`，对不上就从第 2 步重来
6. 每条增量里的数量是**绝对值**（不是增减），数量为 0 表示删掉这一档

`U` / `u` / `pu` 三个字段和「数量 0 删档」都用 2026-09-20 抓的真实推送核对过，
fixture 在 `market/__fixtures__/binance-depth-diff-2026-09-20.jsonl`。

---

## 三、代码怎么分的

| 文件 | 负责 |
| --- | --- |
| `local-book.ts` | 只管一件事：维护一份 Map + 按上面六条判断序列号。不碰网络、不碰引擎，所以能单测 |
| `market-feed.ts` | 拉快照（排队限速 + 退避）、断线时作废本地盘口、把合成好的盘口当 `book` 事件发出去 |
| `parse.ts` | 解析 `depthUpdate`：增量流**不检查排序**（排序是本地盘口的事），数量允许为 0 |
| `streams.ts` | 订阅地址从 `@depth20@100ms` 换成 `@depth@100ms` |

外面（引擎、WebSocket 推送、REST）看到的还是原来的 `book` 事件，只是档位从 20 变成 200。

**档数怎么定的**：币安快照最多 1000 档，但每 100ms 把 2000 个档位重排一遍不划算。
引擎留 200 档（比原来深十倍），REST `/market/depth` 放开到 200，WS 推送只推前 50 档
（200 档 × 2 边 × 每秒 10 次 ≈ 100 KB/s/币对，浏览器用不到）。

## 四、踩的坑：被币安封 IP

第一版跑起来，19 个币对**同时**拉 1000 档快照（每个权重 20），当场 HTTP 418 —— IP 被封。
更糟的是失败后每秒重试一次，解封瞬间又一起打过去，封禁时间从 508 秒涨到 1244 秒。

改法（两条回归测试盯着，`market-feed.test.ts` 的「快照限速」一节）：

1. **排队限速**：快照请求进队列，按 250ms 间隔逐个发。19 个币对约 5 秒铺满
2. **指数退避**：失败后 1 → 2 → 4 … 最多 60 秒，不再定频重试
3. **快照取 500 档**（权重 10，是 1000 档的一半），反正只留 200 档

REST 客户端本来就有限流暂停（429 / 418 时按 `Retry-After` 停一段时间），
但那只是"不再发请求"，挡不住"解封后一起冲"——限速和退避得在调用方做。

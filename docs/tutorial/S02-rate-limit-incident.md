# S02 · 事故复盘：被币安封了 IP

> 日期：2026-09-20 ｜ 代码：`apps/server/src/market/rate-limit.ts`、`binance-rest.ts`、`local-book.ts`、`market-feed.ts`
> 这一讲不在原计划里，是 S01 上线当天出事故临时补的。
> **不贴大段代码**：读完你应该能自己判断这五个改动对不对，而不是去读实现。

---

## 一、那天发生了什么

S01 把盘口从「20 档完整快照」换成「增量流 + REST 快照」之后，第一次连真实行情，日志开始刷这个：

```
[binance-rest] /fapi/v1/depth 被币安限流（HTTP 418），暂停 1131 秒
[market] BTCUSDT 拉盘口快照失败，稍后重试
```

而且暂停时间一次比一次长：**508 → 868 → 1244 秒**。

这不是币安在为难你，是**我们自己在给自己加刑期**。要讲清楚为什么，得先懂两件事。

---

## 二、背景一：币安的限流是怎么回事

官方规则（`docs/vendor/binance/usds-futures.txt` 的 Limits 一节，2026-09-20 核对）：

| 状态码 | 含义 |
| --- | --- |
| **429** | 超速警告。「你太快了，慢一点」 |
| **418** | **已经封你 IP 了**。触发条件是——**收到 429 之后你还继续发** |

三条关键性质：

1. **限额按 IP 算，不按 API Key。** 换个 Key 没用，换个客户端也没用。我们这台机器就是一个额度。
2. **封禁时长按累犯递增，从 2 分钟到 3 天。**
3. **被封期间每撞一次，刑期就往后延一次。**

第 3 条是这次事故的核心。打个比方：

> 你被保安拦在门外，告诉你「20 分钟后再来」。
> 你每敲一次门，保安就说「好，重新算，再加 20 分钟」。
> 我们当时是**每秒敲一次，19 个人一起敲**。

所以被限流之后，唯一正确的动作是：**一个包都不发，老老实实等够 `Retry-After`。**

这个道理代码里本来就写对了——有一个「暂停闸门」，被限流之后直接拒绝所有请求，连网络连接都不建。

**问题是这个闸门从来没生效过。**

---

## 三、背景二：盘口为什么要对序列号

S01 之前，我们订的是「每 100ms 一份前 20 档完整快照」——每条推送都是完整的，拿来直接用，不用管顺序。

S01 之后改成了**增量**：币安只告诉你「哪几档变了」。好处是能拿到几百档深度，坏处是**增量必须严丝合缝地接起来**，中间漏一条，后面全错。

币安给每条增量编了号。想象成一本流水账：

```
…… → 第 111~120 条 → 第 121~130 条 → 第 131~140 条 → ……
```

我们要做的是：
1. 先打开增量流，把推送**攒着**（还不能用，因为不知道账本的起点在哪）
2. 去拉一份**快照**（REST 请求），快照会告诉你「我是截止到第 130 条为止的状态」
3. 把攒着的增量里，第 130 条以前的全丢掉
4. 从**跨过第 130 条的那一批**开始接着往下记

第 4 步是这次第二个 bug 的案发现场。

---

## 四、五个问题

### 问题 1：闸门接错了线 —— 主因

**症状**：被封之后还在不停发请求，刑期越滚越长。

**原因**：闸门的「现在是否暂停中」这个状态，是记在**客户端对象**里的。而代码里拉快照的那一行，是**每拉一次就新建一个客户端**。

比喻：

> 闸门的设计是：「进门时看一眼门上的牌子，写着『暂停中』就别进」。
> 但实际代码是**每次进门都换一扇新门**——新门上永远是空白的，牌子永远写不上去。

所以那句「被限流就暂停」的逻辑，一次都没执行过。19 个币对、每秒重试一次，全部实打实打到了币安。

**这里有个值得记住的教训**：这段逻辑的**单元测试一直是绿的**。因为测试里只建了一个客户端，闸门当然有效。出事的是**接线**，不是逻辑。测试绿 ≠ 接对了。

**怎么改的**：把闸门拆成一个独立的东西（`rate-limit.ts`），全进程只建一个，所有要连币安的地方都从它走——包括拉快照、查 K 线、分层表每日同步。因为币安是按 IP 算额度的，**「现在还能不能发」这件事，整个进程只能有一个答案**。

---

### 问题 3：快照比推送新 → 白白重拉 —— 另一个主因

> （先讲 3 再讲 2，因为 2 是我修 1 的时候自己造的）

**症状**：盘口频繁报「序列号断了」，于是反复重拉快照。每拉一次就是一次 REST 请求，19 个币对一起来，平时就在悄悄逼近限额。

**原因**：回到第三节那本流水账。正常情况是这样的：

```
攒着的推送：  [111~120] [121~130]
快照说：      我截止到第 130 条
              ↑ 第 [121~130] 这批正好「跨过」130，从它开始接 ✓
```

但 REST 快照经常比 WebSocket 推送**跑得更快**——快照已经回来了，覆盖那一段的推送还在路上：

```
攒着的推送：  [111~120]              ← [121~130] 还没到！
快照说：      我截止到第 130 条
              ↑ 攒着的里面一条都接不上
```

这时代码直接认为「对齐完成」，然后用一条**更严格**的规则去判后面的推送：「下一条的『上一条编号』必须正好等于 130」。

可 `[121~130]` 这批推送的「上一条编号」是 **120**，不是 130。于是被判成「断档」→ 重拉快照。

**但它明明是接得上的**——它跨过了 130，完全符合币安文档第 4 条。

比喻：

> 快照说「我记到第 130 条为止」。
> 下一批流水是「第 121 到 130 条」。
> 这批当然接得上，130 就在它里面。
> 但代码非要求下一批必须**从 131 开始**，于是把一批好好的流水扔了，重新去要一份账本。

**怎么改的**：快照之后的**第一批**单独判，两种接法都认——「跨过快照点」和「紧挨着快照点」。从第二批开始才用严格规则。

**这里也有个教训**：我第一版只写了「跨过」那一半，把「紧挨着」这个最常见的情况也判成断档了。**是一条既有的测试当场变红拦住的**，不是我自己看出来的。既有测试就是这么用的。

---

### 问题 4：出事时的日志永远是错的

**症状**：断档日志长这样：

```
序列号断了：pu=120，本地 lastUpdateId=-1
```

那个 `-1` 是假的。真实值是 130。

**原因**：代码先「清空状态」（把编号抹成 -1），下一行才去拼这句日志。于是**每一条断档日志印的都是 -1**。

而 `-1` 恰恰是排查问题 3 时最该看的那个数字。等于这行日志从上线起就是废的。

**怎么改的**：清空之前先把数字存下来。一行的事，但它决定了下次出事你能不能看懂日志。

---

### 问题 2：我自己造的一个新问题

修问题 1 的时候，我顺手加了个限制：「这个币对正在等重试，就别重复排队了」。

方向对，但**管得太宽**：盘口连接断线重连之后，本地盘口已经全部作废、急着要新快照，却被断线前那个「最长 1 分钟」的等待挡在门外。等于重连后要白等最多 1 分钟才能恢复。

**怎么改的**：断线时把这些等待状态一起作废。

**职责要分清**：防限流是闸门（问题 1）的事，「别对同一个币对连着猛拉」才是这个限制该管的。我当时让后者兼职去干前者的活，才管过头了。

---

### 问题 5：一个还没量的性能疑虑

每来一条增量，都要把整张盘口表**拷一份、整个排序、再取前 200 档**。19 个币对 × 每秒 10 次 × 买卖两边。

代码注释里担心的是「2000 档」。但 S01 订的是**全量增量流**，盘口表不封顶在 1000，会一直涨到整本账的深度。

实测（本机）：

| 盘口表大小 | 单次耗时 | 19 币对满速时占用 |
| --- | --- | --- |
| 500 档 | 0.023 ms | 0.9% CPU |
| 2,000 档 | 0.033 ms | 1.3% CPU |
| 10,000 档 | 0.156 ms | 5.9% CPU |
| 40,000 档 | 0.863 ms | **32.8% CPU** |

**2026-09-20 当晚量完了，结论是：不用治。**

接上真实行情，每 30 秒记一次 ETHUSDT（最大的那个）的档位数：

```
 32s  4904
 62s  5529   +625
 92s  6134   +605
122s  6578   +444
152s  6766   +188
182s  6899   +133   ← 增量连续衰减，在收敛
```

**它不是无限涨的**，而是收敛到 7000 档上下（单边约 3450）——这就是那个币对真实挂单覆盖的价位数量，涨到头就不涨了。

按实测规模重新跑基准（19 个币对各自的真实大小）：

| | 结果 |
| --- | --- |
| 19 个币对各排一次（双边） | 0.460 ms |
| 每秒 10 次 | **0.46% CPU** |
| 服务器进程实际占用 | 10～17%（含 WebSocket 解析、撮合、HTTP，全部在内） |

0.46% 淹没在噪声里。**这个问题不存在。**

还顺手验证了一件更重要的事：多出来的几千档**没有污染盘口顶部**。拿我们的盘口和币安权威盘口逐档对：

| | 买一～五 | 卖一～五 |
| --- | --- | --- |
| 我们 | 2573.54 / .53 / .52 / .51 / .50 | 2573.55 / .56 / .57 / .58 / .59 |
| 币安 | 2573.54 / .53 / .52 / .51 / .50 | 2573.55 / .56 / .57 / .58 / .59 |

一个不差。涨上去的都在深处的尾巴里，只占内存不产生假价格。

**这一条留下来的教训是：我当初的担心方向对，但量级判断错了。** 我按「可能涨到 40000 档」推演出 32.8% CPU，实际是 6899 档 / 0.46%。
差了七十倍。**没量之前动手改，改的是一个不存在的问题**——而且会为此把一段正确的代码改复杂。

## 六、这次真正该记住的三件事

1. **单元测试绿，不代表接线是对的。** 问题 1 的逻辑测试从头绿到尾，事故照样发生。逻辑对 + 接错 = 照样出事。
2. **改之前先写一个「探针」把问题复现出来。** 问题 3 我是先写了一段一定会失败的测试，看着它红了、确认原因，才动手改的。否则很容易改了个不存在的问题，还自以为修好了。
3. **既有测试是护栏，不是负担。** 问题 3 我第一版改错，是既有测试拦下来的。如果当时嫌它碍事改掉它，这个 bug 就带着「测试全绿」的假象上线了。

## 九、解封之后的第一件事

**别急着启服务器。** 先确认 `Retry-After` 那段时间真的过完了。

启动时行情层会立刻给 19 个币对拉快照——新进程的闸门是空白的（它不知道上一个进程被封过），所以**会实打实发出去**。没等够就启动，等于又敲一次门，刑期再往后延。

闸门只能防「同一个进程内的连续撞击」，防不了「重启」。这是它的边界，得心里有数。

**而这个边界到了正式环境会变成一个自动化的陷阱**：守护进程（pm2 / systemd）配了自动重启的话，
「被封 → 启动失败退出 → 自动重启 → 又撞一次 → 封更久」会无人值守地循环下去，上限 3 天。
处理办法记在 `docs/design/02-architecture.md` 的「VPS 要求」一节，**必做的那条是零代码的**：给守护进程配退避重启。

## 十、开发期的一个附带发现：Ctrl+C 杀不干净

事故当天在机器上翻出了 **4 个空转的开发服务器**，最早的一个挂了一天多。

原因不是操作不当。`pnpm run dev` 走 turbo，**turbo 给每个 task 单独开一个伪终端**，task 落在另一个进程组里：

```
你的终端 ttys002              turbo 造的 ttys023
┌──────────────────┐          ┌──────────────────────┐
│ pnpm run dev     │          │  tsx watch           │
│ turbo run dev    │ ───────► │  node src/index.ts   │
│ 进程组 9445      │          │  进程组 9466         │
└──────────────────┘          └──────────────────────┘
        ▲
   Ctrl+C 只打到这里
```

Ctrl+C 的 SIGINT 只送给**当前终端的前台进程组**。服务器在另一个组里，信号到不了，
得靠 turbo 自己转发去杀——没转发成功，服务器就活下来了。

活下来的形状特别坏：**服务器进程本身死了**（端口被占），但 `tsx watch` 监听器还活着。
它没有终端（`ps` 里 TTY 显示 `??`）、你看不见它，但**你一改代码它就拉起一个新服务器**。
攒了四个，就是四套行情连接、四道互不通气的限流闸门，同一个 IP 被反复撞——这是那天封禁一路升级的助推器。

**已经处理**：`apps/server` 的 `predev` 钩子会在每次 `pnpm run dev` 之前自动清一遍
（`scripts/kill-stray-dev.sh`，会跳过正在监听 3000 的那一套）。你照旧 `pnpm run dev` 就行。

想手动查：

```bash
pgrep -fl "tsx.*watch src/index.ts"
```

只调服务端时，也可以绕开 turbo 直接跑 `cd apps/server && pnpm dev`——同一个进程组，Ctrl+C 百分百干净。
